# 实验设计：价值排序 vs 编辑排序

> **文档定位（2026-11-02）**：本文是 Market Loom 的 A/B 实验**设计文档 + 实现边界说明**，不是实验报告。仓库中不存在真实用户、真实曝光、真实转化或显著结果；所有示例基线都来自演示漏斗，且已明确标注为模拟值。代码里真正实现的只有「确定性分组函数 + 事件类型定义 + 硬编码演示漏斗」，排序策略分叉、曝光采集、指标聚合与统计检验均**未实现**。事实清单见 [FACT_CARD.md](FACT_CARD.md)。

## 1. 实验背景与问题

演示产品把「发现 → 详情 → 加购 → 结算 → 订单」作为核心路径。假设：把商品默认的编辑策展排序，替换为按「到手价值」解释性排序（价格/评分/标签等可解释字段），能降低用户的比较成本，让更多列表访客走到详情与加购，并最终提高订单转化。

需要验证的问题不是「页面好不好看」，而是：**在 50/50 稳定分流下，B 组排序是否带来主指标的因果提升，同时不劣化体验护栏。**

## 2. 实验假设

| 编号 | 假设 | 层级 | 方向 | 说明 |
| --- | --- | --- | --- | --- |
| H1 | 价值排序 B 组相比编辑排序 A 组，**详情到加购率**提升 | 机制假设 | 单侧预期为正，检验按双侧 | 排序改变列表首屏的商品价值感知，进而影响详情页的加购决策 |
| H2 | 价值排序 B 组相比编辑排序 A 组，**订单转化率（列表访客 → 完成订单）**提升 | 业务主指标 | 单侧预期为正，检验按双侧 | 最终是否值得上线由 H2 + 护栏共同决定 |

说明：

- H1 是解释「为什么可能有效」的机制假设，用于诊断；H2 是上线决策依据。两者都必须在实验开始前写死，不允许事后按结果替换主指标。
- 本仓库的演示数据不支持任何关于方向的结论；`docs/METRICS.md` 与界面文案中的「目标 +4.0pp」「近 7 日 +2.6%」只是演示标注，不构成效应量证据。

## 3. 指标口径

### 3.1 主指标（H2）

**订单转化率 = 完成订单的去重访客数 / 看到商品列表的去重访客数。**

- 分母事件：`product_list_viewed`（计划口径）。**当前 UI 未触发该事件**，因此真实转化率在现有实现中不可计算。
- 分子事件：`order_completed`。**当前为前端模拟下单成功即触发，不是服务端订单确认**（与 `docs/METRICS.md` 的目标口径有差距）。
- 演示口径下的参考值（仅用于样本量演示）：246 / 1,280 = 19.2%。

### 3.2 诊断指标（H1 及漏斗）

| 指标 | 定义（目标口径） | 演示值 | 当前实现状态 |
| --- | --- | --- | --- |
| 详情点击率 | `product_viewed` 去重用户 / `product_list_viewed` 去重用户 | 794 / 1,280 = 62.0% | 分子事件已触发；分母事件未触发 |
| 详情到加购率（H1 主口径） | `product_added` 去重用户 / `product_viewed` 去重用户 | 401 / 794 = 50.5% | 两个事件均已触发；但未持久化、未去重、未按组归属 |
| 加购到订单率 | `order_completed` 去重用户 / `product_added` 去重用户 | 246 / 401 = 61.3% | 事件已触发；演示漏斗没有「结算」步骤 |
| 结算完成率 | `order_completed` / `checkout_started` | 不可计算 | 演示漏斗仅有 4 步，缺结算计数 |

### 3.3 护栏指标

护栏与主指标同样前置定义；**任一项出现统计或业务显著劣化，即停止放量/回滚**：

| 护栏 | 目标口径 | 当前实现 |
| --- | --- | --- |
| 退款率 | 退款订单数 / 完成订单数 | 未实现（无支付/退款） |
| 页面错误率 | 错误页面浏览 / 总页面浏览 | 未实现（无监控上报） |
| P75 LCP | 75 分位最大内容绘制（真实用户监控） | 未实现（无 RUM 采集；`prefers-reduced-motion` 只影响动效） |
| 每单客服咨询率 | 咨询会话数 / 完成订单数 | 未实现（无客服系统） |

护栏指标目前只存在于文档，不可在演示环境中观测——这也是「不能把演示结果当实验结论」的原因之一。

### 3.4 分析单位与去重

- 分组单位：匿名访客（`visitorId`），1:1 分配；同一访客在整个实验周期内固定同组。
- 分析单位：去重访客，intent-to-treat（按分到组统计，不按是否曝光筛选），避免「只统计看过新排序的用户」带来的选择偏差。
- 事件必须带 `variant` 属性才能按组聚合；**当前 `captureEvent` 实际只发送 `product_id` / `price` / `total` / `order_id`，没有 `variant`**（见 [METRICS.md](METRICS.md) 实现状态列）。

## 4. 分流实现（已实现，代码级说明）

`lib/analytics.ts` 中的稳定哈希分流：

```ts
export type ExperimentVariant = "control" | "value-ranked";

export function assignExperiment(visitorId: string): ExperimentVariant {
  let hash = 0;
  for (const character of visitorId) {
    hash = (hash * 31 + character.charCodeAt(0)) >>> 0;
  }
  return hash % 2 === 0 ? "control" : "value-ranked";
}
```

已核对的事实：

- **确定性**：同一 `visitorId` 永远返回同一分组（`tests/commerce.test.ts` 有对应用例）。
- **分配比例**：按 `hash % 2` 奇偶分组；对 `visitor-0 … visitor-9999` 共 10,000 个 ID 抽样，control 占 **50.0%**。
- **映射关系**：偶数 → `control`（界面「A 对照排序」），奇数 → `value-ranked`（界面「B 价值排序」）。实测 `"portfolio-visitor"` → `value-ranked`，`"visitor-42"` → `value-ranked`，`"v2"` → `control`。
- **演示页局限**：`components/storefront.tsx` 把 `visitorId` 硬编码为 `"portfolio-visitor"`，因此所有访客固定进入 B 组，页面**不会同时展示两种排序或两组数据**。
- **排序策略未分叉**：`visible` 始终由 `filterProducts(products, …)` 生成，`variant` 仅用于渲染分组标签；A/B 两组渲染的商品顺序完全相同。PRD/界面中「对照排序 vs 价值排序」目前只是文案与预留设计。
- **生产化建议**：使用带盐的 HMAC-SHA256(visitorId) 映射到 `[0,10000)`，`< 5000` 为 A；`visitorId` 需来自 cookie/账号并持久化；分流在实验开始后不可重算（避免同一用户漂移）。

## 5. 样本量测算

### 5.1 公式与假设

两比例双侧检验，1:1 分组，按每组所需样本量：

```text
n = (z_{1-α/2} + z_{1-β})² × [p₁(1-p₁) + p₂(1-p₂)] / (p₁-p₂)²

α = 0.05（双侧，z = 1.960）
power = 1-β = 0.80（z = 0.842）
n = 每组样本量；总样本 = 2n
```

假设：

1. 对照组基线 p₁ 取**演示漏斗口径**（19.2% / 62.0% / 50.5% / 61.3%），不是线上真实基线；真实基线需接入采集后重算。
2. MDE 同时给出「绝对百分点」和「相对提升」两种表达，便于与产品/业务沟通。
3. 未考虑新奇效应、季节性、流量波动与分组不均衡；工程实现建议再加 10% 缓冲覆盖排除/分桶损耗。
4. 未做多重比较校正（诊断指标仅作解释，不用于上线决策）。

### 5.2 计算结果（α=0.05 双侧，power=0.8，1:1）

| 场景 | 基线 p₁ | MDE | 每组 n | 两组总 n | +10% 缓冲后（每组 / 总计） |
| --- | --- | --- | --- | --- | --- |
| 主指标：列表访客 → 订单 | 19.2% | +2.0pp（≈+10% 相对） | 6,327 | 12,654 | 6,960 / 13,920 |
| 主指标：列表访客 → 订单 | 19.2% | 相对 +10%（→21.1%） | 6,842 | 13,684 | 7,526 / 15,052 |
| 诊断：详情点击率 | 62.0% | +4.0pp | 2,256 | 4,512 | 2,482 / 4,964 |
| 诊断：详情到加购率（H1） | 50.5% | +4.0pp | 2,443 | 4,886 | 2,687 / 5,374 |
| 诊断：详情到加购率（H1） | 50.5% | 相对 +10%（→55.6%） | 1,530 | 3,060 | 1,683 / 3,366 |
| 诊断：加购到订单率 | 61.3% | +4.0pp | 2,274 | 4,548 | 2,502 / 5,004 |

说明：

- 主指标检测 +2pp 需要每组约 6,300 个列表访客，量级明显大于诊断指标；若真实日流量不足以在一个完整业务周期内达到该样本量，应降低置信要求前先与业务确认，或把实验定位为「诊断指标 + 护栏监测」而非主指标显著性判定。
- **以上全部为公式演示**：真实基线、真实 MDE、真实流量均待接入真实数据后确定。仓库中没有真实实验样本，也不存在「样本量已达标」的状态。

### 5.3 运行时长的诚实说明

不编造日流量，因此不给「预计 X 天完成」。上线前需用真实监控数据填入：日去重列表访客数、可分流比例、每周波动，再按「两组总 n ÷ 每日可进入实验人数」估算，并保证覆盖至少一个完整业务周期（含周末/结算周期），同时避开大促等异常窗口。

## 6. 决策规则（实验前写死）

1. **显著且护栏安全 → 上线**：主指标 H2 方向为正、双侧 p < 0.05、95% 置信区间不跨 0，且所有护栏无统计/业务显著劣化。
2. **方向为正但不显著 → 不宣称有效**：不得包装为「提升了 X%」。若样本量未达计划值，按预先约定延长至计划样本量；若已达计划样本量仍不显著，结论为「在当前样本量下未观测到差异」，并基于诊断指标决定是否做更大 MDE 的实验。
3. **方向为负 → 停止**：不扩大放量；回顾诊断指标，判断是排序策略问题还是实验实现问题。
4. **护栏劣化 → 停止/回滚**：即使主指标显著为正，也优先止损（例如错误率或 P75 LCP 超阈值）。
5. **禁止的操作**：提前偷看并多次检验（peeking）、事后更换主指标、剔除不利分组、按分组后筛选细分人群讲故事。若需连续监测，应改用序贯检验/贝叶斯方案并重新估算样本量。
6. **当前仓库的适用范围**：无真实事件数据，因此**不产出任何实验结论**；决策规则仅作为上线前的约定与面试说明材料。

## 8. 上线前置条件（checklist）

- [ ] 真实 `visitorId` 来源与持久化（cookie/账号），实验期间不可变；带盐哈希分流。
- [ ] 真正实现两套排序策略，并保证只有 B 组使用价值排序；策略可回滚。

- [ ] 事件先写入自有存储（可去重、可重算），PostHog 作为可选异步同步目标；成功率监控。
- [ ] 服务端购物车、库存、价格校验、税费与配送规则、模拟支付/订单状态（当前全在前端）。
- [ ] 指标聚合与统计检验脚本（按去重访客、intent-to-treat、按组算 CI/p 值），护栏监控看板。
- [ ] 隐私同意、数据保留策略与事件脱敏（不采集支付凭据、精确地址）。
- [ ] 实验开始前锁定主指标、MDE、样本量、护栏阈值与决策规则；上线评审记录。
- [ ] 真实基线校准：以线上 4 周数据重算样本量；流量不足时先做诊断指标实验。
